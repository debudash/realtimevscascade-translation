# Onboarding a language pair: English ↔ French

Exercise run on 2026-10-15, after the core EN ↔ ES runs passed. The goal: add a pair with
configuration and clips only, then measure what each architecture needed.

**Wall clock:** 06:43:09 → 06:45:07 UTC, about **2 minutes** for the config change, the 4 clips
(ElevenLabs, 178 characters) and a live run through both architectures. That excludes the onboarding
harness spec itself, which is new test tooling rather than product work. Writing the spec took a few
more minutes and is reusable for the next pair.

## Files touched

| File | Change | Needed by |
|---|---|---|
| `server/src/Workbench.Api/appsettings.json` | +1 language (`fr`: name, speaker label, Deepgram `fr`, DeepL `FR`/`FR`) and +1 pair (`en-fr`): 12 lines | both architectures |
| `harness/scripts.json` | +4 evaluation entries (2 EN → FR, 2 FR → EN) with reference translations | evaluation only |
| `harness/clips/enfr-01..02.wav`, `fr-01..02.wav` | generated by `generate-clips.ts` (French speaker: ElevenLabs "Charlie") | evaluation only |

No code changed in either architecture.

- **Realtime:** the server builds the interpreter instructions from the language names, and the
  client retargets the session per press (`session.update` with the direction's instructions and
  transcription language). gpt-realtime, its voice, and gpt-4o-transcribe all handle French.
- **Cascade:** each adapter reads the new language's codes from config: Deepgram nova-3
  `language=fr`, DeepL `FR`, OpenAI by language name, ElevenLabs Flash v2.5 `language_code=fr`.

**Disclosure.** Two pieces of French support were written earlier, while building the clause commit
policy and the report, so the "no code" result relies on them:

- French conjunctions in `ClauseCommitPolicy`.
- French number words and stopwords in `harness/metrics.ts`.

In a fresh codebase these would be the code changes for a new pair: about 10 lines, cascade
clause mode and evaluation only.

## What differs between the architectures

- **Effort to onboard a supported pair:** equal here, because both are a config change. The real
  difference is coverage. Realtime is one vendor model: if gpt-realtime handles a language poorly, there
  is no lever. The cascade can pick a different STT, translator or voice for just that language
  (e.g. a specialist STT for an uncommon language, DeepL or a glossary for terminology), still by
  config once the adapter exists.
- **What each needs per language:** Realtime needs only a language name for the prompt. The cascade
  needs a language code per provider (3 fields), plus a voice choice if the default voice sounds wrong
  in that language.
